# Дизайн-документ: Web Insights & Detailed ML Planning (`web_insayth.md`)

Этот документ содержит выжимку современных (2024-2025) практик машинного обучения из академических статей и индустриальных стандартов, адаптированных под архитектуру **Serpentine Engine**. 

На основе этих инсайтов мы детализируем план разработки для трех новых AI-режимов.

---

## 1. Teacher Mode (Imitation Learning & Behavioral Cloning)

### Восьмиугольный камень преткновения: Качество данных и "Distributional Shift"
Web Research показывает, что слепое клонирование поведения (Behavioral Cloning) часто приводит к "сдвигу распределения" (Distributional Shift). Если агент попадает в состояние, которого не было в обучающей выборке (одна ошибка), он не знает, как вернуться на правильный путь, и ошибка накапливается каскадно.

**Инсайты из Web Research:**
* **Counterfactual Behavior Cloning (Counter-BC):** Современные подходы учат не только "что сделал эксперт", но и "что бы он сделал, если бы ошибся".
* **Фильтрация шума (Suboptimal Data):** Запись каждого кадра может засорить датасет мусорными мискликами оператора.

### Detailed Planning (План интеграции в код):
* **`systems/learning.py (DatasetLoggerSystem)`**:
  * Внедрить **On-Action Recording**. Записывать кадры/состояния не каждый тик (`Continuous`), а только в момент совершения осмысленного действия оператора (`ClickAction`, `TypeAction`). Это сэкономит 90% объема HDF5 файлов и удалит дубликаты.
  * Реализовать **Отложенную запись (Ring Buffer)**: Хранить последние 5 секунд действий в ОЗУ. Позволить оператору в GUI (God Mode) нажать кнопку `[❌ Drop Last Episode]`, если он понял, что ошибся при сборе данных.
* **Форматы:** Каждая запись в датасет представляет собой пару `[Observation, Intent/Action]`.

## 2. Actor-Learner Mode (Asynchronous Online RL)

### Восьмиугольный камень преткновения: Проблема "Stale Policy" (Устаревшие веса)
Исследования архитектуры Actor-Learner (на базе A3C и IMPALA) указывают на проблему "Stale Policies". Актер (в нашем случае движок парсинга сайтов) может использовать устаревшую нейросеть `V1`, в то время как Learner (фоновый процесс) уже вычисляет градиенты для `V3`. Если Актер отправляет опыт, собранный старым мозгом, это дестабилизирует обучение.

**Инсайты из Web Research:**
* Офф-полиси алгоритмы (Off-Policy), такие как SAC (Soft Actor-Critic) или DQN, лучше справляются со Stale Data, так как у них есть Experience Replay.
* Использование "Hogwild!" апдейтов без жестких локов памяти.

### Detailed Planning (План интеграции в код):
* **`core/engine_v2.py (I/O Locks)`**:
  * Точное соблюдение `status = WAITING_FOR_IO` в `BrainComponent`. Мы *обязаны* замораживать агента до полного завершения загрузки страницы, иначе в базу попадут транзитные кадры анимированной загрузки сайта, которые разрушат предсказательную способность модели.
* **`systems/learning.py (ReplayBufferSystem)`**:
  * Каждая запись в буфер должна сопровождаться **тегом версии модели (Model Hash/Version)**.
  * *Пример:* `[Observation, Intent, Reward, NextObservation, model_version="v1.2"]`.
* **`brain/nodes.py (ONNXInferenceNode)`**:
  * Реализовать паттерн **Hot-Swapping**: Использовать `watchdog` или `os.path.getmtime()` для проверки файла `brain.onnx`. Если файл обновился сервером, узел подменяет `onnxruntime.InferenceSession` за 1 миллисекунду прямо в момент I/O блокировки.

## 3. Gymnasium Mode (ECS Mass Vectorization)

### Восьмиугольный камень преткновения: GIL и Коммуникационные издержки
Web Research подчеркивает, что стандартный `gym.vector.AsyncVectorEnv` запускает игры в отдельных процессах Python (`multiprocessing`). Это решает проблему GIL, но создает огромный оверхед на сериализацию/десериализацию данных Pydantic между процессами через Pipe/Sockets.

**Инсайты из Web Research:**
* ECS архитектура (Entity-Component-System) идеальна для RL, так как все данные агентов лежат в едином массиве (C-Contiguous память).
* Нативный `SyncVectorEnv` работает быстрее, если код написан без блокировок.

### Detailed Planning (План интеграции в код):
* **`core/world.py (Memory Layout)`**:
  * Мы не будем использовать `multiprocessing` для Gymnasium среды Змейки. Все 1000 змей будут жить в одном объекте `World`.
  * Каждому агенту выдается `offset_x, offset_y` в пространстве, чтобы "стены" одного вольера не ломали навигацию другого.
* **`core/env_wrapper.py (SerpentineGymEnv)`**:
  * Написать класс, наследующий `gym.Env` (а не `VectorEnv`). Вся магия "массовости" будет скрыта внутри метода `step(actions)`.
  * **Вход:** Массив `actions` размерностью `[1000]`. Обертка раздает 1000 экшенов 1000 агентам через `ActionBufferComponent`.
  * **Tick:** Вызывается ровно **один** `self.engine.tick()`.
  * **Выход:** Собирается массив `observations` `[1000, 10, 10]`, массив `rewards` `[1000]` и массив флагов `terminated`.
  * Это обходит GIL (вся физика считается в едином цикле пересечения множеств) и не требует межпроцессного взаимодействия! Это сделает Serpentine одним из самых быстрых симуляторов для PPO.
